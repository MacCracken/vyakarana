# Security audit — 2026-05-09 (2.0.x closeout)

- **Scope:** vyakarana 2.0.0 → 2.0.3 changes. The streaming
  tokenizer rewrite. Specifically: `tokenize_stream_*` push
  primitive (2.0.0); rolling-buffer drain with `_stream_is_trailing_complete`
  (2.0.1); pull adapter `tokenize_stream_next` and stream-level
  accessors (2.0.2); pending pair-rule fast path with
  `_stream_find_pair_rule` and `_stream_scan_close` (2.0.3).
- **Auditor:** 2.0.4 closeout pass.
- **Trigger:** flagged in the 2026-05-09 1.13-closeout audit's
  recommendations: "When 2.0.0 ships, the first audit should
  confirm the streaming-tokenizer changes don't introduce new
  buffer-bound assumptions that the existing FINDING-002/003/004
  mitigations weren't designed for."
- **Trust model:** unchanged. vyakarana is a library over
  arbitrary input bytes. Streaming makes the input incremental
  but doesn't change the bytes-from-untrusted-sources nature.

---

## Summary

- **New findings:** 0 CRITICAL / 0 HIGH / 0 MEDIUM / 2 LOW.
  Both fixed in-pass (`FINDING-008` _stream_grow zero-cap
  loop; `FINDING-009` _stream_scan_close zero-len matcher).
- **Carryover from prior audits:** 5 LOW (FINDING-002 to 005,
  the defense-in-depth bound checks from the 2026-04-23
  pre-1.0 audit). All status unchanged. FINDING-007 (1.13.3
  audit pass) still fixed.
- **Blocking 2.1.0 release:** none.
- **Posture:** the streaming rewrite added complexity but kept
  the safety contracts intact. Buffer-bound assumptions
  carried forward — `VYK_STREAM_CAP` (16 MB live-buffer cap)
  replaces 1.x's `VYK_SRC_CAP` (1 MB total-input cap), and
  the rolling-buffer compaction means the cap bounds the
  longest in-progress span rather than the cumulative input.
  All scanner reads remain bounded by `buf_len`.

## Surfaces reviewed

### `tokenize_stream_new` / `_feed` / `_free` (2.0.0)

Stream record allocation: `alloc(STREAM_REC_SIZE)` where
`STREAM_REC_SIZE` is now 88 (post-2.0.3). Fixed-size; no
attacker-controlled length.

Buffer allocation: `alloc(VYK_STREAM_INIT_CAP)` = 4096 bytes
at init. Grown by `_stream_grow` (see below).

`_feed(s, chunk, n)` checks:
- `s == 0` → return overflow error (graceful).
- `finished == 1` → return finished error.
- `n <= 0` → return OK (no-op).
- `_stream_grow(s, len + n + 1)` — grows buffer if needed.
  Returns 0 if cap exceeded → feed returns overflow.
- Copy loop bounded by `n`. Destination offset
  `buf + len + i` where `i < n` and `len + n + 1 <= cap`
  (just-grown). Safe.
- Stores final `len + n` to `s + 8`. The `+1` byte for NUL
  terminator is reserved but not written until drain time.

`_free(s)` zeroes every field. Cyrius's bump allocator
doesn't reclaim individual allocations; the doc-comment
already notes this. Buffer memory persists until process
exit.

**No findings on _feed / _new / _free.**

### `_stream_grow` (2.0.0)

The doubling loop `while (new_cap < needed) { new_cap = new_cap * 2; }`
relies on `cap > 0` to make progress. **Pre-fix**: a freed
stream (where `_free` zeroed `cap`) would loop forever if
reused. **Post-fix**: explicit `if (cap <= 0) { return 0; }`
short-circuit before the doubling.

`alloc(new_cap)` where `new_cap <= VYK_STREAM_CAP` (16 MB).
Bounded. The post-clamp `if (new_cap < needed) { return 0; }`
handles the `needed > VYK_STREAM_CAP` case.

Copy loop bounded by `len`, where `len <= cap <= new_cap`.
Safe.

**FINDING-008 (LOW, fixed in-pass):** `_stream_grow` would
infinite-loop on a stream whose `cap == 0` (use-after-free
scenario; `_free` zeroes all fields). Mitigated by an
explicit zero-cap check.

### Rolling-buffer drain + `_stream_is_trailing_complete` (2.0.1)

The full-rescan path (no pending state):

- `tokenize_with_grammar(g, buf, buf_len, temp_tb)` — same
  scanner as 1.x. All scanner reads bounded by `buf_len`,
  unchanged from prior audits.
- Walk `temp_tb`, find `commit_count`. The trailing-complete
  heuristic in `_stream_is_trailing_complete` reads
  `buf + t_start + t_len - 1` where
  `t_start + t_len == buf_len` (the trailing token) — last
  byte read at `buf + buf_len - 1`. Bounded.
- `memeq(buf + t_start + t_len - elen, endp, elen)` — reads
  `elen` bytes ending at `buf + t_start + t_len - 1`.
  Guarded by `elen <= t_len`. Safe.
- Compaction: `store8(buf + dst, load8(buf + k))` where
  `k < buf_len` and `dst < buf_len - consumed`. Source and
  destination both bounded.

`abs_offset` arithmetic: monotonically increasing i64.
At realistic tokenize speeds, takes ~150 years to overflow.
Not a concern.

**No findings on the rolling-buffer drain.**

### Pull adapter (2.0.2)

`tokenize_stream_next(s)`:
- Null check on `s`.
- `idx = load64(s + 64)`.
- If `idx >= count(staging)`, drain to refill.
- If still exhausted, return 0 (EOF).
- Else `store64(s + 64, idx + 1)`; return 1.

`tokenize_stream_kind/_start/_len(s)` read the staging at
`idx - 1`. If `_kind` is called before any successful `_next`,
`idx == 0`, so `idx - 1 == -1`, and `tokenbuf_kind(staging, -1)`
would underflow. The docstring explicitly says "Behaviour is
undefined if called before the first successful `_next`",
so this is a documented contract. No mitigation required;
caller honours the contract.

Staging tokenbuf grows monotonically across iteration. For a
1 M-token stream, staging holds ~12 MB. Documented memory
cost; flagged in state.md as a future optimization
("discardable staging buffer"). Not a security concern at
the bytes level — purely memory pressure on the consumer's
process.

**No findings on the pull adapter.**

### Pending pair-rule fast path (2.0.3)

`_stream_find_pair_rule(g, buf, start, len, kind)`:
- Walks `pair_rules`. For each, `memeq(buf + start, startm,
  slen)` where `slen <= len` and the caller's invariant is
  `start + len <= buf_len`. Bounded.

`_stream_scan_close(buf, buf_len, from, endp, elen, escape)`:
- Loop `j + elen <= buf_len` makes `load8(buf + j)` and the
  `memeq(buf + j, endp, elen)` both safe.
- Escape-byte branch advances `j += 2`; loop condition
  re-checks. Worst case `j` ends at `buf_len` (or one past),
  loop terminates.
- **Pre-fix**: if `elen == 0` (malformed grammar with
  `end = ""`), `memeq(buf + j, endp, 0)` returns 1 vacuously,
  function returns `j == from` immediately, caller pushes a
  zero-length token. Coverage invariant violated. **Post-fix**:
  explicit `if (elen <= 0) { return (0 - 1); }` short-circuit.

Pending-state transitions:
- Set in normal-path drain when an uncommitted trailing
  pair-rule partial is detected. The `_stream_find_pair_rule`
  call confirms a real pair rule emitted it; if not, no
  pending state set (token waits for finish).
- Cleared in fast-path drain after close found, or in
  finish-mode drain when emitted as the final pair token.
- `scan_resume` advances monotonically within the current
  buffer; resets on close or compaction.

The `elen - 1` back-off in `scan_resume` calculation handles
close markers straddling the buffer boundary. Verified by
the 2.0.3 tcyr probe that splits `*/` across two feeds.

**FINDING-009 (LOW, fixed in-pass):** `_stream_scan_close`
would vacuously match at `from` if `elen == 0`, producing
zero-length tokens that violate the coverage invariant.
Mitigated by an explicit zero-elen check. The CYML loader
should also reject empty `end = ""` markers but that's a
separate hardening pass.

### Buffer cap semantics

`VYK_STREAM_CAP` raised 1 MB → 16 MB in 2.0.1. The
significance is **what** it caps, not the absolute number.
1.x `VYK_SRC_CAP` capped total input bytes per file. 2.x
`VYK_STREAM_CAP` caps the *live buffer* — bytes currently
in-flight, between commits. After each compaction, the buffer
shrinks to "longest in-progress span + most recent feed".
Total stream input is unbounded.

This means:
- A 1 GB file with normal token density (no megabyte-spanning
  strings) streams comfortably under a few KB of live buffer.
- A pathological file containing a single 16 MB string
  literal hits the cap and `_feed` returns
  `VYK_ERR_OVERFLOW`. The consumer can either stop or
  retry with a different grammar.
- `VYK_STREAM_CAP` itself is a well-bounded constant; no
  attacker-controlled multiplication or addition that
  could overflow.

The `FINDING-003` carryover ("file-size cap relies on
`VYK_SRC_CAP`") still applies to the CLI's
`VYK_SRC_CAP = 1 MB` cap in `src/main.cyr` (unchanged in
2.0.x). Library consumers using the streaming primitive
directly use `VYK_STREAM_CAP` and aren't subject to the CLI
cap.

## Fuzz / stress / lint posture (2.0.3)

- **Fuzz:** 3/3 harnesses pass. The `tokenize.fcyr` random
  byte sweep exercises the streaming wrapper indirectly via
  `_t_tokenize`. Direct fuzz of the streaming primitive
  (random feed sequences, random chunk sizes) would catch
  pending-pair edge cases the current corpus doesn't exercise.
  Flagged for a future cut.
- **Stress:** 778 tcyr probes total; the 2.0.x groups (push,
  rolling, pull, pending-pair) each have dedicated stress
  probes. The 100-chunks-of-10-bytes-inside-an-open-comment
  case in 2.0.3 specifically validates the O(N) optimization.
- **Lint + fmt:** mandatory pre-release per CLAUDE.md
  §Gates.

## Recommendations

1. **No further code changes.** Both new findings fixed in-pass.
2. **CYML grammar loader hardening.** `_gp_close_rule` should
   reject pair rules with empty `start` or `end`. Today the
   `_stream_scan_close` zero-elen guard catches the runtime
   symptom; rejecting at load time is cleaner. Out of scope
   for 2.0.4; flagged for 2.1.x or whenever a grammar author
   trips the case.
3. **Streaming-aware fuzz harness for 2.1.x.** Random feed
   sequences (varying chunk sizes, random splits across
   multi-byte tokens) would exercise the rolling buffer +
   pending-pair paths the existing corpus-based fuzz misses.
4. **Discardable pull-adapter staging.** Already flagged in
   state.md. Not a security finding (memory pressure, not
   bytes-level vulnerability) but worth doing for very long
   streams.
5. **Next audit:** 2.1.x closeout (after the four grammar
   batches land). Surface additions there are mostly
   declarative `.cyml` files; the audit should confirm no
   grammar-loader hardening regressed.
