# vyakarana — 2.3.x hardening / security audit

- **Date:** 2026-08-20
- **Version audited:** 2.3.3 (fixes shipped as **2.3.4**)
- **Toolchain:** `cyrius 6.5.32`
- **Scope:** full §Hardening-step sweep per `CLAUDE.md` — memory
  safety, integer/truncation, untrusted-input boundaries, streaming
  state machine, deferral language, doc/dead-code drift.
- **Method:** six independent audit lenses over the tree, then
  adversarial verification of the high-severity findings, then
  hand-reproduction of every claim kept below. Nothing in §Fixed is
  reported on an agent's say-so; each has a reproduction recorded
  here.

> **Why this audit was overdue.** The previous closeout audit is
> `2026-05-09-2.1.x`. Everything in 2.2.x and 2.3.x — the vendored-
> stdlib move, two toolchain jumps, the streaming discard primitive,
> the compose-region rule type, and the 37-grammar `TK_ERROR`
> adjudication — shipped without one.

|----------|------:|---------------:|-------------------:|

Gates after the sweep: build OK · **898/898** tests · smoke OK ·
lint+fmt exit 0 · fuzz 4/4.

**Two themes run through almost every finding.**

1. **Silent degradation was the default failure mode.** Oversize
   source, oversize grammars, failed allocations, and >4 GiB stream
   offsets all produced *plausible wrong output with a zero exit
   status* rather than an error. Four separate fixes below convert
   silence into a loud failure. This is now the house rule: a
   tokenizer that cannot honour the coverage invariant must say so.

2. **The gates asserted the right things on inputs too narrow to
   exercise them.** The streaming fuzz harness has asserted
   chunk-invariance since 2.1.4 and passes — while 9 of 14 real
   corpora violate it. The smoke suite has enforced the coverage
   invariant since M1 — over corpora that never approach the 1 MiB
   cap where it breaks. This is the same root cause the 2.3.2
   `TK_ERROR` audit identified ("one canonical sample per grammar
   means a shape the sample lacks is a shape the gates never
   tested"), and it has now bitten twice.

## P1 — Fixed

### P1-1 — `vyk` silently truncated any file over 1 MiB
`src/main.cyr` · FINDING-003, open since 2026-04-23 · **closed**

`file_read_all(path, buf, VYK_SRC_CAP - 1)` stops once it has filled
`maxlen`. Nothing compared `n` against the cap, so a larger file was
tokenized to its prefix and reported success.

**Reproduced.** A 1,500,027-byte shell script:

```
exit=0   stderr: (empty)   tokens: 249,339
grep UNIQUE_TAIL_MARKER -> absent
```

~450 KB — 30% of the file — discarded with no diagnostic and exit 0.
The coverage invariant, which is the published correctness contract,
silently stopped holding at the cut point. 1 MiB is not exotic:
minified JS, generated sources and vendored bundles routinely exceed
it.

**Fix.** `too_large_error()` + a cap check; exit 3. Largest accepted
file is `VYK_SRC_CAP - 2` = 1,048,574 bytes, because a read of
exactly `maxlen` is indistinguishable from a truncated one.
Regression test added to `scripts/smoke.sh`; it fails against the
pre-fix binary with `exit 0 (expected 3)`.

### P1-2 — Compose prefix-hold was near-cubic; documents hung
`src/tokenize.cyr` · found by 3 of 6 lenses

`_stream_compose_prefix_hold` case (b) tested "is byte *k* inside an
already-emitted `TK_PUNCTUATION` token" — an O(`n_temp`) scan — for
**every byte position**, then applied the cheap `memeq` start-marker
test second. Both conditions must hold, so the ordering was pure
cost. It runs per compose rule, twice per drain, and the rolling
buffer does not compact while a compose opener is held.

There were **two** independent multipliers, both fixed:

1. the conjunct ordering above, and
2. `_stream_compose_prefix_hold` being called **twice per drain with
   identical arguments** — `buf`, `buf_len`, `temp_tb` and `n_temp`
   are all unchanged between the two call sites, so the second call
   recomputed the first's answer. A flat 2× on the most expensive
   thing in the drain. Now cached at a scope enclosing both.

**Reproduced.** Valid HTML with one inline `<style>` block, fed in
4 KB chunks with a drain after each — the shape a browser-ish
consumer actually produces:

| input | before | after | speedup |
|------:|-------:|------:|--------:|
| 8 KB | 140 ms | ~17 ms | 8× |
| 16 KB | 1,893 ms | 32 ms | **59×** |
| 32 KB | 19,644 ms | 89 ms | **221×** |
| 64 KB | (extrapolated minutes) | 293 ms | — |

Unterminated `<style>` — the pathological case — was worse and
improved more:

| input | before | after | speedup |
|------:|-------:|------:|--------:|
| 8 KB | 716 ms | 17 ms | 42× |
| 16 KB | 4,267 ms | 38 ms | **112×** |
| 32 KB | 28,399 ms | 100 ms | **284×** |
| 64 KB | did not finish in 90 s | 310 ms | — |

An unterminated markdown fence over 220 KB now completes in 264 ms.
Growth is ~O(N^1.6), down from ~O(N^2.3–2.9).

**Fix.** Swap the two conjuncts so `memeq` runs first, and memoize
the duplicated call. Both are semantically neutral — verified by
re-running the full chunk-invariance sweep and getting byte-identical
divergence counts before and after, plus 898/898 and smoke.

**Not fixed:** the buffer still does not compact while a compose
opener is held. See §Deferred — that part is a design decision, not
a bug to patch.

### P1-3 — Chunked streaming closed strings on *escaped* quotes
`src/tokenize.cyr`

The pending-pair `scan_resume` back-off subtracts `elen - 1` so a
multi-byte close marker straddling the boundary is not missed. For
single-byte markers — JSON and most string rules, `endp = "\""`,
`elen = 1` — that is a back-off of **zero**. A buffer ending on `\`
resumed at exactly `buf_len`, so the next feed's `"` was examined
with its escaping backslash already behind the resume point.

**Reproduced**, `tests/corpus/concept.json` at chunk=3, token #281:

```
single-feed : len=50  ["Scanning until '\"' — breaks on escaped quotes"]
chunked     : len=19  ["Scanning until '\"]
```

The string closed on the escaped quote and everything after it was
mis-tokenized.

**Fix.** After the `elen` back-off, walk back over a trailing *run*
of escape bytes. Backing off the whole run (not one byte) is what
makes it sound: `\\` is an escaped backslash, so resuming one byte in
would mis-pair it, whereas the byte before a maximal run is by
definition not an escape, so the run start always begins a fresh
pair. Runs are short, so this stays O(N). JSON chunk-invariance went
from divergent to **0/7 chunk sizes differing**.

### P1-4 — Shebangs with interpreter arguments failed detection
`src/detect.cyr`

`_detect_shebang` scanned the **whole first line** for the last `/`,
space or tab, so any interpreter *argument* captured the word start.

**Reproduced** — every one of these returned exit 4, "no grammar
matched":

```
#!/bin/bash -e
#!/bin/sh -eu
#!/usr/bin/python3 -u
#!/usr/bin/env -S python3 -u
```

`-e` and `-eu` are ordinary in real scripts, so extensionless shell
and python files were being rejected wholesale. The existing smoke
probe only covers the argument-free `env python3` form, which is why
this survived.

**Fix.** Take the basename of the *first* word; for `env`, skip over
`env`'s own options (`-S`, `-i`) to reach the real interpreter. Seven
regression cases added to `scripts/smoke.sh`; they fail against the
pre-fix binary.

> Note: the first attempt at the `env` option-skip reintroduced the
> exact two-`if` hazard described in P2-1 — mutating `j` and then
> re-testing `load8(src + j)` at the new position. Caught by testing
> rather than by reading. The pattern is a genuine footgun of the
> no-`break` dialect style.

## P2 — Fixed

### P2-1 — One-byte out-of-bounds read in `_ds_scan_tag`
`src/grammars/default_scanner.cyr` · found by 2 lenses independently

```
if (_ds_is_tag_byte(load8(src + p)) == 1) { p = p + 1; }
if (_ds_is_tag_byte(load8(src + p)) == 0) { done = 1; }
```

The first `if` increments `p`; the second re-reads at the new `p`
**without re-testing `p < src_len`**. A tag running to the end of the
buffer reads `src[src_len]`.

The two verifiers split on severity and both were partly right: the
read is **value-neutral** (the function returns `src_len` either
way), so there is no behavioural effect — and it is a genuine OOB
read that faults when `src_len` ends on a page boundary, which one
verifier reproduced as a SIGSEGV. `vyk` masks it by NUL-terminating
at `buf[n]`; `tokenize_with_grammar` is public surface and a consumer
handing over an exactly-sized buffer is exposed.

**Fix.** Read once per iteration, advance only when the byte was a
tag byte. (`_ds_scan_to_lf` immediately below looks like the same
pattern but is safe — it increments last, so the loop condition
catches `p == src_len`.)

### P2-2 — Stream offsets past 4 GiB wrapped silently
`src/tokenize.cyr` · FINDING-005 — **see §Ledger defect**

`Token.start`/`Token.len` are u32 (ADR 0002). `abs_offset` is an i64
accumulating over every byte ever fed.

**Reproduced** directly against `tokenbuf`:

```
pushed start = 4294967301 (2^32 + 5)  ->  read back 5
pushed len   = 4294967303 (2^32 + 7)  ->  read back 7
```

Past 2³² every token start wraps to a small number, so a consumer
indexing `src[start .. start+len)` reads unrelated bytes with no
error signal anywhere.

**Fix.** `VYK_OFFSET_CAP`; `tokenize_stream_feed` returns
`VYK_ERR_OVERFLOW` rather than emitting wrapped offsets. Verified: a
normal feed returns `VYK_OK`, a feed crossing 2³² returns
`VYK_ERR_OVERFLOW`. Widening `Token` is a layout change needing an
ADR and a minor bump, so 2.3.4 does the patch-safe half — refuse the
input instead of corrupting the output.

### P2-3 — Oversize grammars were parsed truncated
`src/grammar.cyr` · FINDING-004 / FINDING-007

Both loader paths degraded silently: the blob path *clamped* to
`GRAMMAR_FILE_CAP - 1` (FINDING-007's fix — memory-safe, but it then
parsed a grammar cut mid-rule as if complete), and the file path had
no truncation check at all. A truncated grammar yields a tokenizer
that is subtly wrong, which is worse than one that is absent.

Not currently reachable — the largest bundled grammar is 6,722 B
against a 32,768 B cap — so this is defence for the day a grammar
grows. **Fix:** both paths `return 0`, which `bootstrap_grammars`
turns into "language not registered". All 45 still register.

### P2-4 — `alloc()` return values unchecked
`src/token.cyr`, `src/tokenize.cyr` · FINDING-002, open since
2026-04-23 · **closed**

`alloc` returns 0 on OOM, on a negative size, and on anything over
`ALLOC_MAX` (2 GiB). Four sites wrote through the result unchecked;
a failed grow stored a NULL data pointer and the next push wrote
through it. Fixed at `tokenbuf_new`, `_tokenbuf_grow`, `_stream_grow`
and the `tokenbuf_push` path.

`tokenbuf_push` **keeps its always-`0` return** — it ships in
`dist/vyakarana.cyr`, so turning it into a status code would silently
change meaning for any consumer that tests it (CLAUDE.md §Do not).
On failure it drops the token rather than corrupting the heap;
callers that care compare `tokenbuf_count` across the call.

### P2-5 — `tokenize_stream_feed` integer overflow
`src/tokenize.cyr`

`needed = len + n + 1` wraps i64 negative for an absurd `n`, making
`_stream_grow`'s `cap >= needed` test trivially true — it returns
success *without growing* and the copy loop runs off the end of the
buffer. Only a garbage length from the caller reaches it, but the
failure mode is an unbounded OOB write. One compare.

### P2-6 — `drain` over-reported `emitted`
`src/tokenize.cyr`

`emitted` was incremented unconditionally, including for tokens
`tokenbuf_push` dropped under allocation failure. `emitted` is what
the caller uses to decide whether more tokens are available. Now
counted from `tokenbuf_count` across the loop.

## P3 — Fixed

- **`tokenize_stream_free` poisoned `pending_idx` to `0`**, but the
  "none" sentinel is `-1` and `0` is a valid pair-rule index. `free`
  deliberately zeroes every field, and two sites lean on that ("_free
  zeroes every field" in `_stream_grow`; the staging guard in
  `_discard_consumed`), so this one field broke the poison contract.
  Currently unreachable — drain's `buf_len == 0` early return and
  `_stream_grow`'s `cap <= 0` guard both fire first — but relaxing
  either would expose `vec_get(pair_rules, 0)` on a NULL grammar.
- **Pull-adapter accessors** `_kind` / `_start` / `_len` lacked the
  `s == 0` and `staging == 0` guards that `_next` and
  `_discard_consumed` already have, and indexed `idx = -1` before the
  first `_next` — a 12-byte read *before* the tokenbuf allocation.
  Now return 0. Cannot break a correct consumer, which never reaches
  those paths.
- **Four present-tense references to `tokenize_source`**, removed in
  2.0.0 (`src/token.cyr`, `src/main.cyr`, `src/grammar.cyr` ×2).
  Historical references that say "was removed" were left alone.
- **`CLAUDE.md`'s frozen-API rule named `tokenize_source`** — so the
  actual 2.x contract was unguarded. Now names the
  `tokenize_stream_*` surface and notes that
  `tokenize_source_handcoded` is a diagnostics oracle outside the
  rule.

## Ledger defect — how FINDING-005 went missing

The canonical definitions in `2026-04-23-audit.md` are:

- **FINDING-005** — `Token.start` / `Token.len` are u32
- **FINDING-006** — unsanitized path/flag echoed to stderr

Both the `1.13` and `2.1.x` carryover tables instead record:

```
| FINDING-005 | LOW | Open — `_sanitize_for_stderr` truncates at first ctrl byte. |
```

Two consequences, and the second is the expensive one:

1. **That description is factually wrong about the code.**
   `_sanitize_for_stderr` *replaces* control bytes with `?` and does
   not truncate. Verified: `--bo<ESC>[31mgus<BEL>TAIL` echoes as
   `--bo?[31mgus?TAIL` — full string preserved, ANSI defanged. The
   FINDING-006 mitigation works correctly. The ledger has carried a
   phantom open finding for two audits.

2. **The real FINDING-005 fell out of the ledger entirely.** Its
   LOW rating rested on "practical file sizes don't approach this" —
   true in April, when the only entry point was `tokenize_source`
   bounded by `VYK_SRC_CAP` at 1 MiB. 2.0.0 replaced it with a
   streaming API whose own header advertises "Total input can exceed
   this freely", which invalidated the premise. Because the ID was
   occupied by the wrong subject, no later audit re-rated it. It took
   until P2-2 above, four minor lines later.

**Rule going forward:** a carryover table copies the finding's
*title* from the canonical audit, never a re-description. A finding
whose preconditions are changed by an architectural rewrite is
re-rated as part of that rewrite.

## Contract violation — streaming is not chunk-invariant

**Partially fixed; the remainder is the top follow-up.**

`fuzz/streaming.fcyr` states the contract:

> The contract verified here is byte-equivalence: **any chunking
> strategy produces the same (kind, start, len) tokens as a
> single-shot feed of the same source.**

It is violated on real corpora. Differential probe — same file, one
feed vs 7 chunk sizes (1, 2, 3, 7, 64, 512, 4096), comparing every
token's `(kind, start, len)`:

| grammar | chunk sizes differing |
|---------|----------------------:|
| cyml | 7/7 |
| markdown | 5/7 |
| html | 5/7 |
| python | 5/7 |
| rust | 4/7 |
| go | 4/7 |
| vue | 3/7 |
| css | 1/7 |
| toml | 1/7 |
| json, shell, yaml, typescript, javascript, cyrius | 0/7 |

The **coverage invariant holds in every case** — no bytes are lost —
but token *boundaries* shift with chunk size, so a consumer that
streams gets a different tokenization from one that feeds whole.

P1-3 fixed one root cause (json went 3/5 → 0/7). At least two remain,
both flagged by the audit and not yet fixed:

- `_stream_is_trailing_complete` matches **any** same-kind pair
  rule's end marker, so a multi-byte delimiter split across a
  boundary can commit early.
- compose-region routing is not reconstructed across chunk
  boundaries, which is why `cyml` — the grammar 2.3.1 was written
  for — is the worst row in the table.

### And: a held compose opener turns `VYK_STREAM_CAP` into a
### total-input ceiling

`src/tokenize.cyr:87-92` promises "Total input can exceed this
freely" and `src/main.cyr` repeats it. That holds normally but not
while a compose opener is held, because `commit_count` is driven to
0, `consumed` is 0, and the buffer never compacts.

**Isolated directly** — same grammar, same chunk bytes, the only
difference being an unterminated `<style>` opener fed first:

```
(a) html, no compose opener:
      fed_bytes = 32,768,000   (2x VYK_STREAM_CAP)
      last_rc   = 0            (still accepting)
      live_buf_len = 1         (compacts correctly)

(b) html, unterminated <style> opener:
      buffer grows monotonically; run did not complete
      -> reaches VYK_STREAM_CAP and feed returns
         VYK_ERR_OVERFLOW permanently
```

So (a) is exactly the documented behaviour and (b) contradicts it.

**Why this is not a patch fix.** Holding the body is *semantically
required*: `_ds_try_compose_rules` refuses to half-consume a compose
rule whose end marker is absent, so a `<style>` body cannot be routed
to the css grammar until `</style>` arrives. The right fix is to
**bound** the hold — past a threshold, give up on compose routing and
emit the body as `TK_STRING`, which is already what the scanner does
when the inner grammar is missing. That is an observable-behaviour
decision (ADR), not a bug fix.

**Why not fixed in 2.3.4.** Three interacting root causes in the
drain path, and correcting token boundaries is plausibly an
observable-behaviour change for consumers, i.e. ADR-and-minor-bump
territory rather than a patch. Per CLAUDE.md §Task sizing, large
effort gets small bites.

**Why the harness passes.** Its inputs are short synthetic strings
for shell/rust/c/html/python. It lists html and python among them,
yet both diverge on the real corpora. The fix is to run the existing
assertions over `tests/corpus/` — which turns the gate red until the
above lands, so it must go in with the fix, not before it.

Numbers above are reproducible with the probe recorded in this
audit's session; they were measured identically against the pre-audit
2.3.3 tree, so this is long-standing, not a 2.3.4 regression.

## Bubbled up — not defects, decisions for the maintainer

- **No `openqasm` grammar.** `vidya` ships
  `content/lexing_and_parsing/openqasm.qasm` and renders its samples
  *through vyakarana*. 11 of its 12 samples tokenize cleanly;
  `openqasm.qasm` exits 4, "no grammar matched". Adding a grammar is
  feature-sized (corpus + registration + the `45` count asserted in
  `fuzz/grammar_load.fcyr`), so it is not folded into a hardening
  patch.
- **Consumers are materially behind.** `owl`, `cyim` and `vidya` all
  pin `2.2.3`. Measured: 2.2.3 → 2.3.0 is 2 changed lines (the
  version header — the old "byte-identical, bumping buys nothing"
  note was accurate when written), but **2.2.3 → 2.3.3 is 241 changed
  lines, +19,565 bytes**. A consumer on 2.2.3 still emits error
  tokens for Go struct tags, shell backtick substitution and AT&T `$`
  immediates. Bumping now buys correctness.

## Deferral-language audit

Requested explicitly. Every deferral-flavoured phrase in
`src/**`, `grammars/*.cyml`, `docs/**`, `CLAUDE.md`, `README.md`,
`CONTRIBUTING.md` was classified **REAL_PENDING / STALE /
MISPHRASED**.

**Bulk result: mostly legitimate.** "Known gaps" appears in 39
grammar files and "stand-in" in 34; these are ADR-0006-referenced
scope documentation, not deferrals, and were left alone. All 22
"vidya doesn't ship an X reference sample yet" claims were checked
against `vidya/content/lexing_and_parsing/` and **all 22 are still
accurate** — none of those languages overlap vidya's actual sample
set.

**STALE — removed** (each verified against the same file's own
rules):

| file | claim | reality |
|------|-------|---------|
| `c.cyml` | char literals split into 3 operator tokens; needs a `char_literal` ADR | `char_literal = true`; ADR 0010 shipped |
| `rust.cyml` | same, "promoted to an ADR once C shows the same pattern" | same |
| `zig.cyml` | same, plus `\\` multi-line strings "would need a new line-rule shape" | that rule is at `zig.cyml:145` |
| `go.cyml` | raw strings a "trivial follow-on"; rune literals split | rule at `go.cyml:133`; `char_literal = true` |
| `kotlin.cyml` | backtick identifiers "could be added as a pair rule" | rule at `kotlin.cyml:145` |
| `sql.cyml` | MySQL backtick identifiers "not in the ANSI baseline" | rule at `sql.cyml:196` |
| `scss.cyml` | `%placeholder` "would need `%` in ident_start or operators" | `%` is in operators |
| `ocaml.cyml` | polymorphic variants "need to add `` ` `` as operator" | it is in the operator list |
| `asm_x86_64.cyml` | AT&T sigils "punted to a future ADR" | ADR 0020 landed them in 2.3.2 |

**MISPHRASED — reworded** (permanent decisions wearing deferral
language, so they stopped advertising pending work):

- `src/theme.cyr` — "no theme-file format yet ... likely in 1.11.0
  for owl coordination". Export shipped in 1.12.1/1.13.0
  (`--export-theme=vscode|helix|iterm`); import does not exist and
  nothing has asked for it. Doubly stale.
- `src/main.cyr` — `VYK_SRC_CAP` "M5's streaming tokenizer will
  remove this ceiling". M5 landed in 2.0.0–2.0.2; the CLI simply
  never adopted the stream.
- `src/grammars/default_scanner.cyr` — operator-scan optimization
  anchored to "M5 benchmark time". Reworded as a deliberate open
  optimization with the reason it is not yet the profitable lever.
- `src/theme.cyr:24` — "just an i64 tag for now" (2.3.3).
- `grammars/rust.cyml` — "Good enough for now" on numeric suffixes.
- `grammars/c.cyml` — preprocessor mode "ADR-worthy later", now
  anchored to a CHANGELOG entry.

`cyrlint` reports **0 untracked deferrals** across every hand-edited
source file.

## Clean checks — no findings

- **`load8` zero-extends** (verified empirically: `0xC8 → 200`,
  `0xFF → 255`), so `char_class_new`'s `store8(tbl + c, 1)` and
  `char_class_match`'s `load8(tbl + byte)` are in-bounds for the
  256-byte table for every input byte. No high-byte OOB.
- **No grammar feeds a high byte into a char-class spec.** Nine
  `.cyml` files contain non-ASCII bytes; all are in comments.
- **The CYML escape decoder is correct** — its sizing loop and its
  writing loop advance identically, so `di` never exceeds `dlen`.
- **`detect.cyr` is bounds-clean** apart from P1-4's logic error —
  every scan tests `src_len` before reading.
- **No dead code.** Eight functions are unreachable from the CLI
  binary; all eight are live — the pull-adapter API consumers call,
  `kind_is_valid` (test suite), `_grammar_blob_count` (fuzz).
- **No command-injection or path-traversal vector** (re-confirmed;
  no `exec`/`system`, paths come from argv and a hardcoded list).
- **`_sanitize_for_stderr` works** — see §Ledger defect.

## Follow-ups, in priority order

1. **Restore chunk-invariance** (`_stream_is_trailing_complete`
   same-kind matching; compose-region routing across boundaries),
   then point `fuzz/streaming.fcyr` at `tests/corpus/` so the
   contract is actually gated. Likely a minor bump.
2. **Eliminate the residual O(N²)** — the rolling buffer does not
   compact while a compose opener is held.
3. **Widen `Token.start`/`len`** past u32, or formally document the
   4 GiB stream ceiling in the architecture contracts. Needs an ADR
   either way (ADR 0002 is the layout decision).
4. **Decide on `openqasm`** — vidya ships the sample today.
5. **Bump consumers off 2.2.3.**
